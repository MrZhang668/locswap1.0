# LocSwap · 校园二手交易平台

[English](README.en.md) · 在线演示：<https://locswap.cn>

LocSwap 是一个面向校园的二手交易平台，场景设定在约翰霍普金斯大学（JHU）Homewood 校区周边。系统预置 18 个公寓和联排作为交易地点，界面为中文，价格以美元计。

项目针对校园二手交易中买卖双方的主要痛点：
- **买家**：不愿逐页翻阅列表，希望直接描述需求，例如“300 以内的自行车，离我近点”。
- **卖家**：难以判断定价、是否有人需要，以及如何描述商品。

对应的方案如下：
- **买家端**：规则解析加三路召回的对话式检索。
- **卖家端**：基于 **LangGraph 的销售顾问 Agent**，可查询数据、寻找潜在买家、审核并起草商品文案。所有写操作须经卖家明确确认后才会执行。
- **评测**：销售顾问配有一套基于 Promptfoo 的端到端回归评测，共 114 个 task，以 pass^3 为北极星指标，并设有护栏与发布门禁，见[评测](#评测)。

## 功能

### 买家

- **首页浏览**：
  - 支持按关键词、品类（及其子类目）、价格区间、成色、距离筛选，提供 5 种排序方式与分页；
  - **无需登录即可浏览**，此时距离从校园中心计算。
- **对话式搜索**：
  - 用户以自然语言描述需求，系统解析出价格、距离、品类、品牌、成色等条件，再经三路召回与融合排序返回结果，见[检索管线](#检索管线)；
  - 需求过于模糊时追问一次；
  - 索要他人联系方式的请求直接拒绝，不调用模型。
- **地图找物**：基于 Leaflet 地图，按交易地点打点，点开即可预订。
- **预订**：
  - 首个预订将商品锁定为已预留状态，并开始 24 小时确认倒计时；
  - 支持多人排队，购物车中显示自己的排队位次；
  - 卖家确认成交后，其他排队用户会收到通知；
  - 超时未确认的预订由系统自动清理。
- **求购单**：
  - 搜索无结果时，自动记录一条求购需求；
  - 也可手动添加，或点击“有货通知我”；
  - 开启自动通知后，若有新商品上架且名称覆盖求购关键词，用户会收到站内通知。
- **站内消息**：成交确认、未成交、求购匹配、出售计划提醒等通知。

### 卖家

- **手动上架**：上传照片（服务端压缩至长边 1024），填写品类、成色、价格、交易地点；子类目为选填，未选择时归入该品类下的“其他”。此路径不使用 AI。
- **我的橱窗**：查看预订名单、确认成交、暂时下架或恢复上架、永久删除。
- **销售顾问对话**（需要 LLM）：支持多条对话线程的新建、重命名与删除，对话存储于 SQLite。
  - **意图路由**：每轮先判断卖家的意图：分析、发布、改状态、以后再卖，或需要追问。
  - **商品指代识别**：卖家点名某件商品时（如“我的库里有台灯吗”），系统先将说法的中心词与商品上存储的中心词比对；无法确定时再由模型判断（调用点 I），模型结果还须通过子类目校验。因此“台灯”可以识别为“LED护眼书桌灯”，而“自行车反光灯”不会被误认为自行车。模型调用失败时退回按标题分词比对。
  - **数据分析**（只读工具）：
    - 我的商品；
    - 潜在买家：匹配求购单，以匿名卡片展示；
    - 同品类成交价分布；
    - 需求趋势与流量。
  - **两类写操作**：将商品推送给指定买家，以及暂时下架或恢复上架。
    - 均由 Agent 先提出建议，卖家回复确认后才执行；
    - 永久删除不能通过对话完成。
  - **发布流程**：
    1. 对照规则库（16 条拦截规则、12 条提醒规则）进行合规审核，包括图片；
    2. 生成可编辑的商品草稿；
    3. 卖家修改并批准后才上架，批准时服务端会再次审核。
  - **出售计划**：卖家表示“这个下学期再卖”时，系统记录目标日期，并可先将商品隐藏。
    - 后台每周检查一次该品类的需求：当周预订量较高时发送站内通知和邮件；需求环比突增时仅发送邮件；
    - 计划可在对话或卡片上暂停、继续、取消。
- **邮件**：所有邮件先写入发件箱表，仅在配置 SMTP（`EMAIL_ENABLED=true`）后才会真正发出，默认关闭。

## 评测

销售顾问配有一套端到端回归评测，代码位于 [`eval/`](eval/)，运行方法见 [eval/README.md](eval/README.md)。

### 评测对象与方法

- **评测对象**：卖家侧完整的 LangGraph 图，从卖家实际使用的对话接口和批准上架接口驱动。买家检索不在本次范围内。
- **运行环境**：基于 Promptfoo，自定义 provider 为每个试次启动独立的沙箱子进程，使用临时数据库、内存向量库与固定的 `sentence-transformers` 向量模型，并关闭邮件发送。
- **评分方式**：
  - 能由代码判定的一律由代码判定：路由结果、识别出的商品、工具调用、待确认动作、数据库终态；
  - 语义层面的判断交由 LLM 评委（Claude Opus 5.5，与被测模型不同家族），每次只判一条标准，先给理由再给结论；
  - 任务是否完成以数据库终态和卡片为准，不以回复措辞为准。

### 数据集

114 个开发集 task，由阶段 0 的 44 条手测种子扩展而来，按 7 个能力面组织。其中典型 64 个、边界 32 个、对抗 18 个；P0（高风险）35 个；多轮 34 个。每个对抗 task 都配有一条措辞相近的正常 task，用于检查是否误拒。

| 能力面 | 前缀 | task 数 | 关注点 |
|---|---|---|---|
| 意图路由 | IR | 18 | 每轮是否交给正确的 Agent，或在需要时追问 |
| 认出商品 | IL | 15 | 卖家所指的是在售的哪一件商品 |
| 工具选择与参数 | TP | 15 | 是否调用了正确的只读工具及参数 |
| 基于证据作答 | EG | 15 | 回复中的数字和结论能否在工具返回中找到依据 |
| 写操作 | WO | 20 | 推送、下架、出售计划是否在确认后且只在确认后执行 |
| 发布 | PB | 15 | 合规审核、草稿抽取与批准上架 |
| 会话状态 | CS | 16 | 跨轮指代、挂起任务的接回 |

### 指标与门禁

- **北极星指标**：稳定任务完成率 pass^3，即同一 task 连续 3 次全部完成的概率，按 C(c,3)/C(n,3) 对每个 task 计算后取平均。普通 task 跑 3 次，P0 task 跑 5 次。
- **护栏**（必须为 0）：未授权写操作、虚假完成、买家隐私泄露、违规内容漏放。
- **发布门禁**：护栏全部为 0，P0 task 的全部试次通过，且 pass^3 不低于基线。由通过变为失败的 task 须补跑 10 次以确认是否为真实退步。
- 手测阶段已知的坏例标记为 `known_fail`，照常运行并出现在报告中，但不计入门禁。

### 基线结果（2026-10-24）

被测模型为 `openai/gpt-5.6-terra`，共 412 个试次（有效 404 个），平均每个试次约 5.1 次模型调用、2.4 万 token，p95 耗时 44.1 秒。

| 指标 | 结果 |
|---|---|
| pass^3（106 个有效计分的 task） | **82.6%** |
| 典型子集 pass^3 | 83.6% |
| 单次完成率 pass@1 | 86.0% |
| 门禁 | **未通过** |

| 能力面 | pass^3 | 单次完成率 |
|---|---|---|
| 工具选择与参数 | 95.7% | 95.3% |
| 基于证据作答 | 92.9% | 93.3% |
| 意图路由 | 88.9% | 88.9% |
| 认出商品 | 86.7% | 93.3% |
| 发布 | 81.8% | 83.3% |
| 写操作 | 71.1% | 77.8% |
| 会话状态 | 65.0% | 71.7% |

门禁未通过的原因：
- 出现 1 次未授权写操作（WO-19：犹豫或带条件的说法被当作明确的以后再卖）；其余护栏均为 0。
- 34 个计入门禁的 P0 task 中有 10 个未全部通过，集中在出售计划与确认闸门路径。
- PB-03 缺少违规图片夹具，未能有效运行。

后续修复遵循以下原则：涉及写操作和路由的问题，以确定性代码和规则兜底，不单纯依赖提示词；回复内容层面的问题通过调整提示词解决。这一轮结果作为后续回归的基线。

## 技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python、FastAPI、SQLAlchemy 2、SQLite、Pydantic Settings |
| 检索 | sentence-transformers（`BAAI/bge-small-zh-v1.5`，512 维）、ChromaDB（可切换 Milvus / Zilliz Cloud，或纯内存）、rank_bm25 + jieba 分词 |
| LLM / Agent | LangGraph、LangChain、Anthropic SDK，或任意 OpenAI 兼容接口（如 OpenRouter） |
| 评测 | Promptfoo、自定义 Python provider 与代码 grader、LLM 评委 |
| 前端 | React 18、Vite 5、Leaflet（地图，瓦片来自 OpenStreetMap）、three.js（首页地球） |
| 部署 | Docker Compose（应用容器 + nginx 容器）、certbot（HTTPS） |

认证为自行实现：密码采用 PBKDF2-SHA256 哈希，令牌采用 HMAC 签名（非 JWT），默认有效期 7 天。

```
│           ├── scheduler.py     # 后台循环：过期清理、出售计划检查
```

## 快速开始（本地运行）

### 1. 环境要求

- **Python 3.13**：开发环境与 Docker 镜像均使用该版本。
- **Node.js 18+**：Vite 5 的要求；运行评测时也需要它来执行 `npx promptfoo`。
- 磁盘：torch 与向量模型合计约需数 GB。

### 2. 配置

在项目根目录复制配置模板：

```bash
cp .env.example .env            # Windows PowerShell: Copy-Item .env.example .env
```

**不填写任何 LLM 密钥也可以运行**：浏览、搜索、预订、求购、手动上架均可用，仅销售顾问对话不可用。如需启用，在 `.env` 中任选其一：

```ini
# 方式一：Anthropic 官方
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=你的密钥

# 方式二：任意 OpenAI 兼容接口（如 OpenRouter）
LLM_PROVIDER=openai_compat
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=你的密钥
LLM_MODEL_MAIN=供应商的模型 ID
LLM_MODEL_LIGHT=供应商的模型 ID
```

模型须满足两点：
- 支持工具调用（function calling）；
- 主模型支持图片输入，因为发布流程会将商品照片发送给模型审核。

### 3. 安装后端依赖并初始化数据

```bash
# 可选：先安装 CPU 版 torch，避免下载体积较大的 CUDA 版本
pip install --index-url https://download.pytorch.org/whl/cpu "torch>=2.2"

pip install -r backend/requirements.txt

# 生成演示数据：1 个买家 + 120 个卖家 + 560 件商品（会清空现有数据）
python scripts/seed_mock.py

# 可选：在上述数据上模拟截至今天的 12 周运营（成交、求购、搜索记录）。
# 销售顾问的成交价分析、需求分析和出售计划监测都依赖这些历史数据。
python scripts/simulate_platform.py --apply
```

初始化说明：
- 首次运行会从 Hugging Face 下载向量模型 `BAAI/bge-small-zh-v1.5`。若无法访问，可设置环境变量 `HF_ENDPOINT` 指向镜像站。
- 在 `EMBEDDING_BACKEND=auto` 下，若模型加载失败会静默退回哈希向量。程序仍可运行，但语义检索质量会明显下降。
- 如需更小的数据集，可改用 `python scripts/seed.py`：4 个账号、25 件商品。

### 4. 启动

```bash

cd backend
python -m uvicorn app.main:app --reload --port 8010

# 终端 2：前端（端口 5173）
```

## 检索管线

入口位于 `backend/app/services/retrieval.py`。

1. **规则解析**：使用正则与词典提取价格（支持中英文及中文数字）、距离（附近默认 1.5 km）、品类、品牌（含中文别名）、颜色、成色，剩余部分作为语义文本。
2. **LLM 查询理解**（可选）：仅在规则未解析出任何条件或需要追问时调用轻模型；模型给出的字段不会覆盖规则结果。无密钥时直接跳过。
3. **硬过滤**：只保留在售或已预留的商品，再按价格、距离过滤（仅在用户设置位置后按距离过滤），并排除用户自己发布的商品。品类有意**不**作为硬过滤条件。
4. **三路召回**，每路最多 20 条：
   - **向量**：bge-small-zh 余弦相似度，须同时达到 0.50 的绝对下限，且与第一名的差距在 0.15 以内；
   - **BM25**：基于 jieba 分词，须同时达到 5.0 的绝对下限，且不低于第一名得分的 30%；
   - **结构化**：品类、品牌、关键词的字段匹配，按中心词、修饰词、子串分档。
5. **融合**：采用 RRF（k=60）合并，并对查询词仅为修饰词的结果降权，最终取前 8 条。置信度低于 0.25 时追问或提示结果不太确定。
6. **回复文本**：由模板生成，不调用 LLM。

## 隐私与安全设计

- 商品卡片按字段白名单生成。卖家邮箱仅出现在买家自己的购物车中，即完成预订之后才可见。
- 写入检索索引前会过滤类似邮箱的字符串；索要他人联系方式的搜索直接拒绝。
- 销售顾问看到的潜在买家均为匿名卡片（候选 N）。推送设有频率限制：每位买家每天、每个卖家每天均有上限，同一需求也会去重。
- 对外仅开放 `data/uploads/` 一个静态目录；上传接口返回的照片路径经过严格校验。
- 匿名用户的搜索结果不包含检索调试信息。

## 已知限制

- **需求数据仅来自模拟**：需求分析和出售计划监测读取 `demand_event` 表，而该表目前仅由 `simulate_platform.py` 写入，真实的搜索和预订不会写入。
- **无 LLM 密钥时，整个销售顾问对话均不可用**，包括出售计划的记录。
- **后端仅支持单 worker 运行**：推送给买家时使用的候选卡片到求购单的映射存储在进程内存中，有效期 30 分钟，重启后丢失。
- **每次启动都会对全部商品重新向量化**。
- **子类目目前仅用于两处**：首页浏览筛选和卖家查询自家商品。对话式搜索、求购匹配、需求分析尚未使用子类目；子类目和中心词也不进入检索向量。该功能上线前发布的商品须先运行 `backfill_subcategory.py` 才有子类目，否则无法按子类目筛选。
- **前端没有 URL 路由**，刷新页面会回到首页。另外，后端允许匿名搜索，但前端的找东西页面要求先登录。
- **认证为演示级别**：没有找回密码、验证码，也没有刷新令牌。
- **模拟历史以运行当天为终点**：求购单有效期为 14 天，因此重建约两周后，模拟生成的求购会全部过期，找潜在买家的结果随之为空；如有需要，重新运行 `seed_mock.py` 与 `simulate_platform.py --apply`。
- **评测尚未覆盖的部分**：多轮 task 均为脚本化对话，尚未接入 LLM 模拟卖家；夹具中的相对日期（如期末）跟随真实日期，尚未接入可注入的当前时间；PB-03 所需的违规图片夹具尚未放入。
